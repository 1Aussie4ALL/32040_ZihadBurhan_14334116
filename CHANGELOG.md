# Changelog

A record of what changed in this prototype, newest first. Entries are derived from the git
history — each one names the commit it came from, so the code behind any claim here can be
read directly.

Dates are commit dates. Test counts are the totals reported at that commit.

> This is a change log, not an evaluation. Measured results live in
> [`docs/evaluation-results.md`](docs/evaluation-results.md), which is regenerated by
> `npm run evaluate` and should not be edited by hand.

## `main`

### 2026-10-21 — Assessment and review fixes; validation branch merged

Found by driving the running app end to end rather than calling the pipeline directly. Fix
commit `a124120`; tests added for every item.

- **The patient's assessment ignored their answers.** The booking wizard ran the assessment
  with the previous render's answer set, which on the first pass was empty — so every
  patient saw "Insufficient Information" and the 000 emergency warning never appeared, even
  for the README's own cardiac demo. The stored result and clinician queue were unaffected,
  because the server recomputes triage at submission; this is also why the unit,
  integration and scenario tests, which exercise the pipeline directly, did not catch it.
  Present since `1cd60de`. A new component test (`tests/bookingWizard.test.tsx`) drives the
  wizard and checks what is sent for assessment.
- **A failed assessment was invisible.** The spinner and error/retry view live on the
  assessment step, which was only shown on success. The wizard now moves there first.
- **Clinician review:** an override without a reason is rejected by the server, not only the
  form; saving a note on a reviewed request no longer silently un-reviews it and clears its
  review time; an unchanged override is no longer re-audited on every save.
- Merges `validation-and-view-switcher` (below) into `main`.

## Merged from `validation-and-view-switcher` (2026-09-25, merged 2026-10-21)

### Visible form validation (`68aa72e`, 2026-09-25)

Responds to supervisor feedback that the inline error under a form was easy to miss and did
not say what was actually missing.

- On a failed submit, every form now flashes the fields needing attention and opens a centred
  pop-up listing each problem. "Show me" scrolls to the first field and focuses it. Covers all
  booking steps, the contact form, the clinician login, and the override reason.
- The doctor and appointment `Continue` / `Confirm` buttons were previously disabled with no
  explanation. They now stay enabled and state what is missing.
- Error messages name the real problem instead of "enter a valid …":
  - **Email** — commas, spaces, missing `@`, missing ending after `gmail`, `..`, invalid
    characters.
  - **Mobile** — Australian mobiles only (`04` + 8 digits). Landlines, `+61` format, wrong
    prefix and wrong length each get a distinct message.
  - **Date of birth** — future dates, and dates before 1900.
  - **Questions** — what each question type requires ("Please choose Yes or No", "move the
    slider …").
- The details step now validates against the **same schema as the server**. A looser client
  check previously let values through (`name@gmail,,,.com`, `0412.345.678`) that the server
  rejected only at final submit, with one generic message.
- If the final submit does still fail, the server returns field-level errors. The pop-up names
  the step and problem ("Your details: Email can't contain commas"), "Go to Your details"
  opens that step with the field marked, and after the fix the patient returns to the
  appointment step with their chosen time preserved.
- Fixes the severity slider showing a midpoint number the patient never chose and then
  refusing to continue. It reads "Drag or tap the slider to answer" until set, and tapping the
  thumb in place counts as an answer.
- The concern step now enforces the server's 1000-character limit.

New: [`src/components/common/ValidationPrompt.tsx`](src/components/common/ValidationPrompt.tsx),
[`src/lib/validation/bookingErrors.ts`](src/lib/validation/bookingErrors.ts),
[`src/lib/validation/email.ts`](src/lib/validation/email.ts),
[`src/lib/validation/patientDetails.ts`](src/lib/validation/patientDetails.ts), plus
`tests/bookingErrors.test.ts`, `tests/emailValidation.test.ts`,
`tests/validationPrompt.test.tsx`.

### Patient / Reception view switcher (`3ad8f30`, 2026-09-25)

- A switcher in both headers makes the full loop quick to demo: book as a patient, switch to
  Reception, see the request in the queue, switch back.
- Reception goes straight to the dashboard. With nobody signed in it signs in as the seeded
  demo receptionist with no password — **only under `next dev`**. A production build always
  routes to the normal login page; `tests/demoViewSwitch.test.ts` asserts this.
- Patient returns to the last patient page visited (`sessionStorage`), not the home page.
- On phones the reception header shows only the logo icon (with an `aria-label`) and uses
  tighter padding, so the switcher fits without sideways scrolling at 390px.

New: [`src/components/common/ViewSwitcher.tsx`](src/components/common/ViewSwitcher.tsx),
`tests/demoViewSwitch.test.ts`.

### Lockfile and install scripts (`ef69944`, 2026-09-25)

- `npm ci` refused to install: `package-lock.json` was missing `@emnapi/runtime` and
  `@emnapi/core`. Resynced via `npm install`.
- npm 11 holds back package install scripts until approved. Approves those the app needs —
  `prisma`, `@prisma/client`, `@prisma/engines` (query engine), `esbuild` (used by `tsx` and
  `vitest`), and `unrs-resolver` (used by `eslint`). `fsevents` is deliberately left
  unapproved: it is an optional macOS watcher that ships prebuilt.

## Earlier history on `main`

### 2026-09-16 — Error handling, integration tests, evaluation (`24f9e40`)

Completes work packages 6.1–6.6. 74 tests (up from 47); typecheck, lint and build clean. 404
handling verified against a running production server.

- **6.1 — Error handling.** The app had no error boundaries, so a thrown server error hit
  Next's default screen. Adds route-level boundaries for the patient and clinician trees, a
  global-error boundary for root-layout failures, and a custom 404. Each is written for its
  actual clinical risk: patient-facing boundaries repeat the 000 advice and state that nothing
  was assessed or submitted; the clinician one says explicitly that a load failure must not be
  read as an empty queue. `global-error` inline-styles everything, since a stylesheet that
  failed to load could be the reason it is showing.
- **6.2 — Testing.** Adds `tests/booking.integration.test.ts`, running against a real SQLite
  database rather than mocks: the `submitAppointmentRequest` transaction, structured answers
  surviving the JSON round-trip, slot claiming (including double-booking and wrong-doctor
  rejection), stale cross-category answers being excluded from storage, urgency-ordered queue,
  clinician override with audit attribution, and review idempotency. `tests/globalSetup.ts`
  creates and disposes a throwaway `prisma/test.db`, so the demo database is never touched.
  This replaces the manual smoke test that `testing-evaluation.md` admitted was not kept in
  the repo.
- **6.3 — Scenario runs.** Adds `scripts/run-evaluation.ts` (`npm run evaluate`), which runs
  all 26 scenarios through the real pipeline and regenerates `docs/evaluation-results.md` plus
  a JSON artifact. Every number in that report is produced by the code, so it cannot drift
  from what the system actually does.
- **6.4 — Workflow comparison.** Rather than arguing the case in prose, adds two models of
  conventional booking (`no_triage` and a deliberately generous `keyword_triage`) and scores
  them over the same 26 scenarios: **19.2%** and **50.0%** accuracy against the system's 100%,
  with **0%** and **83.3%** emergency recall against 100%. The informative cases are
  `SCN-EDGE02`, where the risk exists only in a structured answer and no keyword scan can find
  it, and `SCN-R05`, where "blood pressure medication" trips a keyword and is wrongly
  escalated.
- **6.5 — Assessment.** Adds an information-completeness metric (8.0 clinical data points per
  request versus 1.0 for a free-text form) and a heuristic usability evaluation. The report and
  README both state plainly that 100% measures **self-consistency, not clinical validity**,
  since the scenarios and their expected urgencies are the author's own.
- **6.6 — Assessment.** Adds
  [`docs/safety-explainability-assessment.md`](docs/safety-explainability-assessment.md): an
  explainability audit, a 10-row hazard analysis with residual risk ratings, and privacy and
  security assessments. Notes that the reception role is displayed but **never enforced**, so a
  reception user currently sees the full structured symptom history.

### 2026-09-16 — Rebuild as a single Next.js app; scope and validate answers (`1cd60de`)

Replaces the CarePrior microservices prototype (6 FastAPI services, 2 Next.js apps, Docker
Compose) with one Next.js 16 application backed by SQLite/Prisma. The earlier build is
preserved under [`_archive/careprior-v1/`](_archive/careprior-v1/) for reference. 11 new tests
(47 total, up from 36).

- **Scopes adaptive questions to the selected complaint category.** Several follow-ups unlocked
  on a generic trigger (`core_severity >= 7`) with no category check of their own, so a
  high-severity abdominal complaint was being asked the cardiovascular sweating and fainting
  follow-ups.
- **Drops stale answers from a previously selected category** before they reach the safety-rule
  engine. A patient who answered the cardiac red flags, then went back and changed category to
  musculoskeletal, had `SR-002-CARDIAC-WARNING-CLUSTER` fire against an ankle injury.
- **Validates every structured answer against the question bank that produced it**
  ([`src/lib/validation/answers.ts`](src/lib/validation/answers.ts)): declared type, option list
  and scale range. Invalid values are rejected rather than coerced, because a coerced answer
  could move the final urgency in either direction, **including downwards**. Previously
  `core_severity: 999` reached the AI scoring layer unchecked.
- Un-anchors the `node_modules` / `.next` / `__pycache__` ignore rules so the archived v1
  build's dependencies and build output are not committed.

### 2026-07-29 — Login fix: strict `EmailStr` rejected `.local` demo addresses (`e1a34e4`)

Running the full stack live — rather than only import-checking it — surfaced that pydantic's
`EmailStr` treats `.local` as a reserved special-use TLD and rejects it, which blocked every
seeded demo account from logging in. `LoginRequest.email` became a plain `str`: login security
comes from password verification, not email-format strictness.

### 2026-07-29 — CarePrior vertical slice (`6667fb8`)

Implements the brief's case-study scenario end-to-end — adaptive questioning → deterministic
rule engine → mock AI interpretation → precedence-combined prioritisation → staff
review/override → append-only audit — across `api`, `ai-service`, `rule-engine`,
`prioritisation-service`, `audit-service` and `notification-service`, with `patient-portal` and
`staff-dashboard` Next.js frontends. Adds a Docker Compose environment, README run
instructions, a Phase 1 discovery doc, and a supervisor pitch page. 36 tests.
